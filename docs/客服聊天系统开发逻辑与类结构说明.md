# 客服聊天系统开发逻辑与类结构说明

---

## 1. 项目定位与总体结构

这是一个面向人工客服场景的实时聊天系统。普通用户可注册、登录、发起咨询、发送文字或附件、查看历史会话与工单；客服可上线接待、转接会话、管理快捷回复和工单；管理员可管理用户、角色与权限，并查看会话、工单、统计和运行状态。

业务范围包括人工客服接待、实时消息和会话闭环。

### 1.1 技术栈

| 范围 | 采用技术 | 用途 |
| --- | --- | --- |
| 后端 | Java 17、Spring Boot 4、Spring WebSocket/STOMP | HTTP 接口、实时双向消息、定时任务 |
| 鉴权 | Apache Shiro、Redis Token | HTTP 身份识别、角色/权限控制、Token 注销 |
| 数据访问 | MyBatis-Plus、MySQL 8 | 实体映射、会话/消息/工单等持久化 |
| 实时状态 | Redis 8 | 在线心跳、排队、客服负载、消息热缓存、分布式锁和补偿队列 |
| 文件 | MinIO、LibreOffice | 附件对象存储；Office 文件预览转换 |
| 前端 | Vue 3、Vite、Pinia、STOMP 客户端 | 三类角色工作台与实时连接管理 |
| 部署 | Docker Compose | 应用、MySQL、Redis、MinIO 的一键编排 |

### 1.2 Maven 模块与职责边界

```text
application                 启动模块、HTTP/STOMP 入口、鉴权配置、调度器
    ↓
businessModel               业务编排、Redis 状态、消息/会话/附件/工单服务
    ↓
commonModel                 实体、DTO/VO、Mapper、常量、异常、通用返回结构
    ↓
third-party-libs            三方依赖收敛模块

frontend                    Vue 前端，不参与 Maven 打包；Docker 构建时单独编译
sql                         新建数据库时使用的建表脚本
```

依赖方向为 `application → businessModel → commonModel`。`commonModel` 保存通用模型与数据访问定义；业务服务通过接口与上层连接；Controller 位于入口层。

### 1.3 运行时组件关系

```text
浏览器 Vue  ──HTTP──> Spring Boot ──MyBatis-Plus──> MySQL
    │                       │
    └──STOMP/WebSocket───────┤
                            ├──Redis：会话状态、队列、锁、消息缓存
                            └──MinIO：附件原文件和预览文件
```

HTTP 负责登录、资料、管理和文件接口；STOMP 负责会话发起、聊天、输入状态、消息确认、已读、撤回、转接和心跳。MySQL 保存最终业务数据，Redis 保存实时状态和可靠性补偿数据。Redis 状态缺失时，业务流程会查询 MySQL 并回填活动索引。

## 2. 模块功能说明

### 2.1 账号、认证与权限模块

**主要类**

| 位置 | 类 | 职责 |
| --- | --- | --- |
| HTTP 入口 | `AccountController` | 注册、个人资料、修改密码、恢复码与找回密码 |
| HTTP 入口 | `ChatAuthenticationController` | 登录、退出登录、签发 WebSocket 临时票据 |
| 业务层 | `AuthenticationServiceImpl` | 校验账号状态、密码、角色和权限后完成登录 |
| 业务层 | `TokenServiceImpl` | 创建、解析、注销 Token，维护用户的全部登录 Token 索引 |
| 业务层 | `UserAccountServiceImpl` | 用户自助注册、资料和恢复码管理 |
| 配置层 | `ShiroConfig`、`StatelessAuthFilter` | 将 Bearer Token 解析为当前用户并建立鉴权上下文 |
| 数据层 | `SysUserMapper`、`SysUserRoleMapper`、`SysRolePermissionMapper` | 用户、角色、权限关系查询 |

**功能边界**

- 注册只创建普通用户；管理员、客服角色由权限管理模块分配。
- HTTP 请求使用 `Authorization: Bearer <token>`；Token 在 Redis 中映射到用户 ID，同时维护 `user:tokens:{userId}`，可支持单 Token 注销和注销全部会话。
- WebSocket 不直接把长期 Token 放入 URL。前端先调用 `/chat/ws-ticket` 获得一次性、30 秒有效的临时票据，再在握手阶段消费票据。
- Controller 只做参数校验、当前用户获取和权限入口；账号状态、角色和权限的实际判断集中在服务层。

### 2.2 用户、角色与权限管理模块

| 入口/服务 | 已实现能力 |
| --- | --- |
| `UserController` + `UserServiceImpl` | 用户分页、关键字查询、创建、编辑、重置密码、删除、分配/移除角色、VIP 等级维护 |
| `RoleController` + `RoleServiceImpl` | 角色和权限的分页查询与 CRUD，角色—权限绑定 |
| `RbacServiceSupport` | 统一处理权限编码、默认角色/权限约束和关系检查 |
| `WorkspaceRoleResolver` | 根据当前用户角色决定前端进入用户、客服或管理员工作台 |

角色描述身份（如用户、客服、管理员），权限编码约束具体管理动作。管理接口通过 Controller 中的 `require...Permission()` 进入权限校验。

### 2.3 实时聊天与会话路由模块

聊天业务由路由、消息、在线状态、转接和通知等服务组成，`ChatServiceConfiguration` 负责显式装配：

| 类 | 单一职责 |
| --- | --- |

| `ChatMessageDeliveryService` | 发送消息时的校验、限流、幂等、实时推送、离线缓存、异步落库登记 |
| `ChatMessageManagementService` | 历史分页、已读回执、未读数、撤回与编辑缓存同步 |
| `ChatMessageService` | 将发送类和管理类消息能力组合为对外接口 |
| `ChatPresenceService` | 在线登记、心跳、输入状态、断线和客服重连宽限期 |
| `ChatSessionTransferService` | 会话转接、负载迁移和转接日志 |
| `ChatAgentService` | 客服上下线、VIP 技能缓存、上线后恢复会话 |
| `ChatOfflineMessageService` | 向离线用户暂存消息，重新连接后拉取 |

STOMP 入口均位于 `ChatStompController`，客户端发送的目的地为 `/app/chat.*`；服务端向特定用户推送时使用 `/user/queue/...`。前端的 `frontend/src/services/stomp-client.js` 负责连接和订阅，`chat-connection.js`、`chat-session-actions.js` 与 `chat-agent-actions.js` 分别拆分连接、会话和客服端动作。

**主要类**

| 位置 | 类 | 职责 |
| --- | --- | --- |
| 业务层 | `ChatMonitoringMetrics` | 基于 Micrometer 登记并更新落库时延、锁等待、锁失败次数和 WebSocket 在线数 |
| 业务层 | `ChatMonitoringService` | 组装运行快照，读取 Redis 队列/死信基数，Redis 不可用时降级 |
| HTTP 入口 | `ChatManagementController` | 向管理员暴露运行快照接口 |

**功能边界**

### 2.8 工单闭环模块

| 位置 | 类 | 职责 |
| --- | --- | --- |
| HTTP 入口 | `SupportTicketController` | 会话工单查询、创建、更新、历史分页、管理员筛选和用户反馈 |
| 业务层 | `SupportTicketService` | 参与者校验、状态流转、版本冲突处理、历史登记和提交后通知 |
| 数据层 | `SupportTicketMapper` | 工单明细、管理员组合筛选和各状态数量统计 |
| 数据层 | `SupportTicketStatusHistoryMapper` | 按工单保存和分页读取操作轨迹 |
| 前端状态 | `chat.js` | 当前工单、历史记录、表单脏状态和远端更新冲突提示 |

每个会话最多关联一个工单。当前负责客服可以创建和更新工单，普通用户只能操作自己会话中的已解决工单，管理员可按工单编号、文本、状态、优先级、分类、客服和创建时间组合查询。工单编号由数据库主键格式化为 `TK-%08d`；接口接收编号时校验格式并还原主键。

工单状态使用 `SupportTicketStatus` 约束流转，更新时必须携带 `version`。服务层的更新 SQL 同时匹配工单 ID 与旧版本，只有影响一行才算成功，避免客服编辑、用户反馈或多标签页操作相互覆盖。每次创建、状态变化、内容修改、用户确认或重新处理都会写入 `support_ticket_status_history`。

### 2.9 会话查询、元数据、归档与评价模块

`ChatSessionQueryServiceImpl` 集中承载不改变实时路由关系的会话扩展操作：我的会话分页、排队状态、用户侧栏、评价、标题/优先级/分类/标签、归档和归档统计。

| 能力 | 权限和数据边界 |
| --- | --- |
| 会话列表 | 先按用户或客服身份限定 `user_id` / `agent_id`，再附加状态与归档筛选；未读数、标签和最后消息批量补全 |
| 用户侧栏 | 只有当前会话的负责客服可查看，内容限于用户资料、VIP 等级、会话总数和上次会话时间 |
| 会话评价 | 只有会话发起方可评价已结束会话；数据库主键约束保证每个会话一条评价 |
| 元数据 | 当前客服可修改自己的会话，管理员可修改任意会话；标签统一转小写、去重并限制数量和长度 |
| 归档 | 只允许当前客服归档已结束会话；状态流转由 `ChatConstants.canTransitionTo` 检查 |

该模块以 MySQL 为事实来源，不负责改变客服负载或 Redis 活动会话索引。结束、转接等实时状态变化仍由路由服务处理。

### 2.10 管理查询、报表与人工维护模块

| 类 | 主要功能 |
| --- | --- |
| `ChatManagementQueryServiceImpl` | 客服看板、视图计数、会话列表、管理员概览、报表、会话/消息检索、评分汇总和转接日志 |
| `ChatManagementMapper.xml` | 多表聚合、组合筛选、趋势分桶、客服接待排行、响应时长和满意度统计 |
| `ChatAdministrationService` | 管理员按登录编号创建会话、删除消息、结束并删除会话 |
| `ChatSessionDeletionService` | 在事务内删除工单和会话，事务提交后删除附件对象 |

客服查询始终带 `agentId` 范围；管理员查询可跨客服。会话检索支持用户/客服登录编号、会话状态、归档状态、评分、工单编号、工单关键字、工单状态、是否有关联工单和时间范围。消息检索对客服传入当前客服 ID，对管理员则不加客服范围。

管理员报表按时间范围一次返回会话趋势、客服接待排行、平均首次响应、会话时长分布、满意度和工单状态分布。业务层负责规范时间范围、限制最大跨度并补齐数据库没有返回的时间桶或枚举桶，前端因此可以直接按固定顺序绘图。

### 2.11 配置、异常与可靠性基础模块

| 范围 | 主要类 | 作用 |
| --- | --- | --- |
| 服务装配 | `ChatServiceConfiguration` | 显式创建聊天子服务并固定依赖方向，避免核心服务互相循环注入 |
| 异步执行 | `AsyncConfig` | 分离消息持久化线程池与 STOMP 出站线程池，并配置队列和拒绝策略 |
| WebSocket 安全 | `WebSocketHandshakeInterceptor`、`StompAuthChannelInterceptor` | 消费一次性票据、绑定 `Principal`、校验 CONNECT/SUBSCRIBE 身份和订阅范围 |
| 统一异常 | `WebExceptionAdvice`、`StompExceptionHandler` | 将 HTTP 与 STOMP 异常转换为稳定的客户端错误结构 |
| Redis 原子操作 | `ChatRedisRepository`、`ChatRedisScripts` | 封装锁、续租、集合操作和跨 Key Lua 脚本 |
| 启动校验 | `RuntimeProfileValidator`、`ProductionCredentialValidator` | 在生产配置错误或仍使用弱默认凭据时阻止应用带病启动 |

`ChatRedisRepository` 的锁会返回随机 Token，释放和续租均检查 Token 所有权，不能用普通 `delete` 代替。凡是一次修改多个 Redis Key 的会话操作，应优先复用 `ChatRedisScripts` 中已有脚本，而不是在 Java 中逐条写入。

### 2.12 初始化、数据迁移与后台清理模块

这一组代码平时不直接参与聊天，却决定了系统能否安全启动、旧数据能否迁走，以及长期运行后会不会留下垃圾数据。

| 类 | 实际工作 |
| --- | --- |
| `AdminBootstrapService` | 首次启动时创建默认管理员，并确认该账号仍绑定启用的 `ADMIN` 角色 |
| `ChatAttachmentMigrationRunner` | 根据配置决定是否执行旧附件迁移，避免每次启动都无条件扫描文件 |
| `ChatAttachmentMigrationService` | 把旧目录中的附件搬到 MinIO，逐个核对大小和 SHA-256，再处理旧目录 |
| `ChatAttachmentCleanupScheduler` | 定期调用附件服务删除数据库中已没有记录的对象 |
| `RedisDataRetentionScheduler` | 分批清理已过保留期的死信 payload 和统计数据 |

默认管理员已经存在时，启动逻辑不会重置密码，只补齐 `ADMIN` 角色关系。附件迁移包含上传后的回读校验。只要发现路径越界、文件大小不符、摘要不一致或旧目录中存在未登记文件，迁移就停止，旧目录不会被删除。

### 2.13 核心聊天类关系

聊天模块由入口、消息、路由和在线状态几组服务组成，依赖关系如下。

```text
ChatStompController
  → ChatStompApplicationService：身份、角色、权限和 STOMP 请求参数
      → ChatMessageService：组合发送、历史、已读、撤回、离线消息

```

## 3. 关键业务流程与复杂函数解析

本章按当前实现说明函数逻辑。代码阅读可从 Controller 或 STOMP 映射进入，再沿 service 接口定位实现类和数据访问层。

### 3.1 登录与 WebSocket 一次性票据

**调用链**

```text
POST /chat/login
  → AuthenticationServiceImpl.login
  → TokenServiceImpl.issueToken
  → Redis: token:{token} 与 user:tokens:{userId}

POST /chat/ws-ticket
  → AuthenticationServiceImpl.issueWebSocketTicket
  → TokenServiceImpl.issueWebSocketTicket
  → WebSocketHandshakeInterceptor.consumeWebSocketTicket
  → WebSocketUserPrincipal
```

**`AuthenticationServiceImpl.login(LoginRequest)` 的思路**

1. 通过登录名找到用户，检查账号存在、启用状态和密码匹配。
2. 查询用户角色，形成登录响应中的身份信息。
3. 调用 `TokenServiceImpl.issueToken(userId, rememberMe)` 生成高随机度 Token，并按“记住我”选择不同 TTL。
4. 返回 Token、用户资料和角色；密码散列、恢复码等敏感字段不进入返回对象。

**`TokenServiceImpl` 的关键点**

- `issueToken` 同时写入 `token:{token} → userId` 与 `user:tokens:{userId}`，后一个集合使“修改密码/禁用用户/退出全部设备”能够找全旧 Token。
- `resolveUserId` 会验证 Token 映射有效；`revokeToken` 与 `revokeAllForUser` 同步清理两个索引，保持 Token 索引一致。
- `issueWebSocketTicket` 只在 HTTP Token 已经属于当前用户时签发。票据对应 `ws:ticket:{ticket}`，TTL 为 30 秒，握手消费后即删除，降低 URL 泄漏长期凭据的风险。

**身份约束**：WebSocket 临时票据为一次性票据；STOMP 身份由握手阶段建立的 `Principal` 提供。

### 3.2 用户接入、客服选择与排队

**入口**：`ChatStompController.startConsultation` → `ChatStompApplicationService.startConsultation` → `ChatRoutingSessionService.onUserConnected(userId)`。

```text
用户发起咨询
  ├─ 取得 userId 级分配锁，拒绝并发重复分配
  ├─ Redis 查现有活动会话
  │    └─ 命中且 MySQL 仍是 ACTIVE：恢复索引并通知用户
  ├─ MySQL 查活动会话（Redis 丢失时的兜底）
  │    └─ 命中：回填 Redis 并恢复会话
  ├─ Lua 原子挑选可接待客服
  │    ├─ 有客服：创建 MySQL 会话 → 原子写 Redis 活动索引 → 双方通知
  │    └─ 无客服：写入等待队列 → 推送排队位置
  └─ finally 释放分配锁
```

**`ChatRoutingSessionService.onUserConnected(String)` 的复杂点**

| 机制 | 为什么需要 | 当前处理方式 |
| --- | --- | --- |
| 用户级分配锁 | 同一用户连续点击、重连或多标签页可能同时建会话 | `chat:assign:lock:{userId}`，获取失败即返回处理中状态 |
| Redis + MySQL 双重查找 | Redis 状态缺失时仍需识别现有活动会话 | 先 Redis，后 `findActiveByUserId`，命中后回填缓存 |
| 原子客服预留 | “选出最低负载客服”和“增加负载”若分两步执行会超卖容量 | `RESERVE_IDLE_AGENT_SCRIPT` 在 Redis 内完成 |
| VIP 与反饥饿 | VIP 具有优先级，普通用户保留等待上限 | Lua 选客服结合 VIP 技能/预留槽；队列另有普通用户到期索引 |
| 异常补偿 | MySQL 会话插入失败时需要释放 Redis 预留 | 捕获异常调用 `handleSessionCreationFailure` 回滚预留状态 |

**`findIdleAgent` 的思路**

该方法执行 Lua 脚本，从 `agent:load` 找到未达到 `AGENT_MAX_CONCURRENCY=5` 的候选客服，结合 VIP 技能集合、VIP 预留席位和上次分配时间选出合适人员，同时登记待提交的分配预留。候选选择和容量预留在同一原子操作中完成。

**`cacheActiveSessionState(ChatSession)` 的思路**

MySQL 插入成功后，通过 `COMMIT_ACTIVE_SESSION_SCRIPT` 一次提交下列 Redis 状态：用户当前会话、会话→用户/客服、客服→会话集合、会话元数据、最后活动时间，并清除该用户排队和预留状态。脚本将这组关联索引作为一个原子状态写入 Redis。

### 3.3 消息发送、幂等、实时推送与可靠落库

**入口**：`ChatStompController.handleSend` → `ChatStompApplicationService.handleSend` → `ChatMessageService.handleMessage` → `ChatMessageDeliveryService.handleMessage`。

```text
客户端消息
  → 校验身份、会话参与者、消息类型/内容、附件归属、回复目标
  → 按发送者限流
  → clientMsgId 幂等检查
  → 生成服务端 messageId，登记 persist:pending
  → 写 Redis 最近消息缓存
  → 推送 RECEIVED 回执和对方实时消息；对方离线则写 offline:msg
  → 专用线程池异步写 MySQL
       ├─ 成功：删除 pending，推送 STORED 回执
       ├─ 可确认的重复：核对逻辑消息后按成功处理
       └─ 失败：退避重试，最终转 deadletter
```

**`ChatMessageDeliveryService.handleMessage(ChatMessage)` 的具体思路**

1. 校验消息属于活动会话，发送者确为该会话用户或客服；再根据类型检查文本、回复目标和附件归属。
2. 用 `chat:msg:rate:{userId}` 做用户级时间窗限流，防止单个连接持续刷消息。
3. 使用客户端传来的 `clientMsgId` 建立 `client:msg:dedup:{...}` 幂等键。重复提交会返回已有消息，并保持单次推送和单次落库记录。
4. 在任何异步操作前调用 `MessagePersistService.markPending`，将完整消息 JSON 和待确认 ID 保存到 Redis。这样进程在刚推送后崩溃时，补偿任务仍能取回消息。
5. `cacheMessage` 只保留每个会话最近 200 条热消息；历史查询会在缓存不足时转 MySQL。
6. `routeAndPush` 先向发送者发 `RECEIVED`，再推给在线接收者；接收者不在线时写入其离线列表，等待 `/chat.offline.pull` 拉取。

**`MessagePersistServiceImpl.persistWithRetry` 的具体思路**

| 分支 | 行为 |
| --- | --- |
| 首次/补偿抢到 lease | 给该消息设置带 Token 的 `persist:retry:lease:{messageId}`，防止多个调度器同时落库 |
| 插入成功 | 删除 `persist:pending` 和 payload，记录落库时延，并向发送者推送 `STORED` |
| 唯一键冲突 | 用 `sessionId + senderId + clientMsgId` 查询原记录；内容完全相同视为幂等成功，不同则转死信 |
| 其他失败且未达上限 | 按 `10s → 30s → 60s` 延迟重新提交，续租 watchdog 维持 lease |
| 达最大次数 | 从 pending 移入 `persist:deadletter`，保留 payload 一段时间供管理员重放或删除 |

`MessageReconciliationScheduler` 每 30 秒扫描超过 10 秒仍未确认的待落库消息，重新提交异步任务。它处理的是崩溃、线程池拒绝或普通重试未执行等场景；lease 保证补偿和原任务不会并行写同一条消息。

**推送与离线缓存的可靠性细节**

- 实时推送在会话操作锁外执行。`convertAndSendToUser` 是阻塞调用，客户端连接缓慢或断开时会拉长持锁时间，阻塞同会话的转接、结束和超时处理。
- 推送失败不向外抛出，也不删除 `client:msg:dedup` 去重键。消息已进入待确认列表，客户端可通过离线拉取获得；若因推送失败删键，客户端重试会生成新 messageId，与落库补偿叠加产生重复消息。
- `pullOfflineMessages` 对每条离线消息单独处理。无法反序列化的脏 JSON 会被移除；能够解析但推送失败的消息仍留在列表中，等下次连接后重试。

### 3.4 已读、撤回与历史消息

| 函数 | 思路 |
| --- | --- |
| `ChatMessageManagementService.markMessagesRead` | 校验读者属于会话、锚点消息属于会话后，以 `lastReadMessageId` 为边界批量标记；返回未读数，并通知对方已读结果。 |
| `countUnreadMessages` | 使用 `chat_message_read` 关系表统计未读数。 |
| `recallMessage` | 校验操作者是原发送者、消息仍处于允许撤回窗口；获取会话操作锁后更新 MySQL，再在事务提交后同步 Redis 热缓存并通知对方。 |
| `getHistory` | 校验会话参与者，使用游标/分页读取消息；对引用回复批量补全预览，避免对每一条消息各查一次数据库。 |

会话操作锁 `session:operation:lock:{sessionId}` 同时保护结束、转接、断线清理以及撤回等会改变会话或消息状态的动作。新增此类动作时，应评估是否需要使用同一把锁，避免状态交叉覆盖。

**已读回执的持久化与刷新恢复**

`markReadThrough`（`ChatMessageReadMapper.xml`）以读者选定的锚点消息为边界：先比较 `create_time`，时间相同再比较消息 id（`id <= anchor.id`），批量写入 `chat_message_read`，并用 `ON DUPLICATE KEY UPDATE` 去重。`markMessagesRead` 用同一个 `LocalDateTime` 实例入库并随 `MessageReadResult.readAt` 返回，对方收到推送后即可展示已读时间。

刷新后的已读状态由水位线恢复。`findLastReadWatermark` 按 `create_time DESC, id DESC` 取读者在会话中的最后一条已读，返回消息 id、消息创建时间和已读时间（`MessageReadWatermark`）。`getHistory` 查询对方水位线，组装进 `ChatHistoryPage` 的 `counterpartLastReadMessageId`、`counterpartLastReadMessageCreateTime`、`counterpartLastReadAt` 三个字段。前端收到 `CHAT_HISTORY` 后执行水合：我方消息创建时间早于水位线时间即标记 `readByPeer`；时间相同则比较消息 id，不晚于水位线 id 也算已读；命中的消息附带 `peerReadAt`，用于悬停展示已读时间。

### 3.5 在线状态、心跳、断线与客服重连

**主要方法**：`ChatPresenceService.registerOnline`、`handleHeartbeat`、`handleDisconnect`、`handleHeartbeatTimeout`、`disconnectAgent`。

```text
WebSocket 建连/心跳
  → user:ws、ws:session、user:online、online:heartbeat 更新
  → 临时输入状态写 typing:{sessionId}:{userId}（带 TTL）

断连事件或心跳扫描超时
  → 获取 userId 级 presence lock
  → 判断身份
      普通用户：清理在线状态和排队条目，保留活动会话
      客服：进入重连宽限期，通知关联会话
  → 宽限期仍未重连：枚举 agent:{agentId}:sessions，释放负载，结束/重新路由受影响会话
```

**为什么有两条断线路径**：浏览器正常关闭通常能触发 `SessionDisconnectEvent`，网络中断、进程异常或设备休眠未必能触发。因此 `HeartbeatTimeoutScheduler` 每 10 秒扫描 `online:heartbeat`，90 秒未刷新则走同一套清理逻辑。

**客服重连宽限期**：客服短暂断网后，系统写入 `agent:reconnect:grace` 并通知相关用户。客服在宽限期内重新上线时，`ChatAgentSessionRecoveryService.restoreActiveSessions` 通过 Redis 索引和 MySQL 恢复活动会话；宽限期结束后执行完整断开清理。

### 3.6 会话结束、排队重分配与转接

**`ChatRoutingSessionMaintenanceSupport.endSessionByAgent`**

1. 获得会话操作锁，检查操作者就是该会话当前客服且会话仍为活动状态。
2. 通过数据库事务将会话改为结束状态，并处理负载和会话索引的结算。
3. 在事务成功后向双方推送结束通知；释放出的客服容量会触发 `dequeueAndReassign`，尝试让队首等待用户进入会话。
4. 若 Redis 状态提交失败，保留 `session:finalize:pending` 供会话状态对账任务补偿。

**`ChatSessionTransferService.transferSession`**

1. 校验转出者为当前客服，目标用户存在、启用且具有客服角色，并与原客服不同。
2. 用会话操作锁阻止结束、转接、断线处理并发修改同一会话。
3. 在事务中更新 `chat_session.agent_id`，写入 `chat_session_transfer_log`。
4. 用 Redis 脚本原子地更新原客服和新客服的会话集合与负载；失败时按已有状态回滚。
5. 提交后向用户、原客服和新客服发送转接通知。

**`QueueTimeoutService.removeTimedOutUsers`**

排队主集合 `queue:pending` 使用 ZSET；`queue:enqueued-at` 记录真实入队时间，独立于 VIP 排序分值。定时扫描处理 VIP 与普通用户的超时策略、客服通知和多组队列索引清理。`queue:normal-due` 用于普通用户的反饥饿保障，队列写入逻辑同时维护这些关联 Key。

### 3.7 附件上传与预览

**`ChatAttachmentServiceImpl.upload(userId, sessionId, upload)` 的思路**

1. 先确认 `userId` 是会话参与者；清理文件名路径片段，取得扩展名并执行内容/大小限制。
2. 使用 UUID 生成附件记录 ID 与对象名称，上传原文件到 MinIO。
3. 写入 `chat_attachment` 记录，记录原名、对象名、媒体类型、大小、会话和上传者。
4. 注册事务回调：数据库事务没有提交时删除刚上传的对象，防止对象存储留下无记录文件。
5. 返回不泄露存储凭据的附件元数据；聊天消息以附件 ID 引用时会再次核验附件与会话对应。

**`preview` 的思路**：先进行与下载相同的会话参与者校验。图片、PDF、文本直接返回适合预览的数据。Office 文件按扩展名调用 LibreOffice 转换，转换结果走两级缓存：L1 为进程内 LRU（`LinkedHashMap` 按最久未用淘汰），L2 为对象存储中的持久预览 `previews/{attachmentId}.pdf`。请求先查 L1，再查 L2；L2 命中则回填 L1 直接返回，两级都未命中才执行实时转换，转换成功后同时写 L1 和 L2。L2 读写失败只记日志并降级为实时转换，预览转换失败不影响原文件下载。

xls/xlsx 不经过 LibreOffice，由前端 exceljs 直接解析工作簿渲染为表格。WPS 中文内建日期格式（`numFmtId=58`）在解析时会丢失，前端按“数值落在合理日期序列区间”兜底识别为日期，避免日期显示为序列数字（`xlsx-preview.js`）。

### 3.8 定时任务与状态对账

| 调度器 | 默认周期/触发 | 处理内容 |
| --- | --- | --- |
| `HeartbeatTimeoutScheduler` | 10 秒 | 扫描超时心跳，进入断线处理 |
| `AgentReconnectGraceScheduler` | 5 秒 | 处理客服重连宽限期到期 |
| `QueueTimeoutSweeper` | 15 秒 | 清理超时排队用户并推送提示 |
| `MessageReconciliationScheduler` | 30 秒 | 重试尚未确认落库的消息 |
| `SessionStateReconciliationScheduler` | 30 秒 | 补偿待分配、待结束和 MySQL/Redis 不一致的会话状态 |
| `SessionInactivityScheduler` | 配置化 | 扫描长期无消息活动的会话并执行重路由 |
| `RedisDataRetentionScheduler` | 1 小时 | 清理到期死信 payload、VIP 统计等 Redis 数据 |
| `ChatAttachmentCleanupScheduler` | 配置化 | 删除不再被数据库附件记录引用的对象 |

多实例部署时，调度器通过 `DistributedSchedulerLock` 抢占 `scheduler:lock:*`，并由 watchdog 续约。修改共享状态的调度任务接入该锁后，可以在多实例环境中维持单次执行语义。

### 3.9 工单创建、更新、用户确认与通知

**调用链**

```text
客服创建/更新工单
  → SupportTicketController
  → SupportTicketService.createTicket / updateTicket
  → 校验当前负责客服、状态流转和 version
  → 更新 support_ticket + 写 support_ticket_status_history
  → 事务提交后向会话双方推送 TICKET_CREATED / TICKET_UPDATED

用户反馈处理结果
  → submitUserFeedback
      ├─ CONFIRM：保留 RESOLVED，写 USER_CONFIRMED 和确认时间
      └─ 其他动作：RESOLVED → IN_PROGRESS，写 REOPENED 并清除解决时间
```

**`SupportTicketService.updateTicket` 的具体思路**

1. 将 `TK-00000001` 形式的工单编号校验并还原为数据库 ID，读取工单及所属会话。
2. 要求操作者是会话当前负责客服，并比较请求 `version` 与数据库版本；不一致直接提示刷新。
3. 用 `SupportTicketStatus.canTransitionTo` 检查状态机；目标为 `RESOLVED` 时强制要求处理结果。
4. 组装下一版本数据，通过 `WHERE id = ? AND version = ?` 更新。即使读取后又发生并发修改，更新行数也会变为 0，从而阻止覆盖。
5. 状态变化写 `STATUS_CHANGED`，状态未变但正文或处理结果变化写 `CONTENT_UPDATED`；无实际变化时不制造历史记录。
6. 使用 `TransactionSynchronization.afterCommit` 推送通知。数据库回滚时不会提前通知前端；推送失败只记录日志，不回滚已提交的工单。

**前端冲突处理**：`chat.js` 收到工单更新事件时先刷新历史。若当前表单已经编辑，设置 `supportTicketStale` 提醒存在远端新版本，不直接覆盖本地输入；表单未修改时才自动刷新工单详情。

### 3.10 会话列表聚合、元数据与归档

**`ChatSessionQueryServiceImpl.findMySessions` 的具体思路**

1. `SessionParticipantType` 决定基础范围：普通用户匹配 `user_id`，客服匹配 `agent_id`，不能只依赖前端传入筛选条件。
2. 叠加会话状态和归档状态。`archiveStatus=NONE` 被转换为 `archive_status IS NULL`，与具体归档状态分开处理。
3. 对当前页会话 ID 批量查询未读数、标签和最后消息，再按 ID 组装 `ChatSessionListItemVO`。
4. 最后消息 Mapper 已按会话和时间排序，Java 端通过 `putIfAbsent` 保留每个会话的第一条，即该会话最新消息，避免逐会话查询形成 N+1。

**`applySessionMetadata` 的具体思路**：先校验标题、优先级和分类，再将标签 `trim`、转小写、用 `LinkedHashSet` 保序去重，并限制最多 10 个、单个最多 32 个字符。会话字段更新、旧标签删除和新标签插入处于同一事务，任一步失败会整体回滚。

**`setArchiveStatus` 的并发保护**：归档仅适用于已结束会话，且必须由当前负责客服操作。更新条件除会话 ID 外还包含旧 `archive_status`；旧值为 null 时使用 `IS NULL`。两个页面同时改变状态时，后提交者影响行数为 0，并收到“请刷新后重试”，不会静默覆盖前一个结果。

**评价重复提交**：`rateSession` 先校验会话已结束且操作者为发起用户，再插入以 `session_id` 为主键的评价。若并发或重复提交触发唯一键冲突，服务读取并返回已保存评价，使重试保持幂等。

### 3.11 管理员组合检索与报表组装

**`ChatManagementQueryServiceImpl.searchSessions` 的具体思路**

1. 页码至少为 1、每页最多 100；状态、归档状态、评分和时间范围分别校验。
2. 精确工单编号通过 `parseTicketNo` 转为主键；`ticketKeyword` 保留给标题、问题描述等模糊匹配，两者可以独立使用。
3. 先调用 `countSessionSummaries` 得到总数，再以同一组规范化条件调用 `findSessionSummaries`，保证分页总数与记录条件一致。
4. `hasTicket` 只有为 true 时才形成“必须有关联工单”的条件；其余情况不额外限制。
5. Mapper 在数据库侧联结会话、用户、客服、评价、工单和最后消息，业务层只负责权限范围、参数规范化和分页包装。

**`findAdminReportOverview` 的具体思路**

```text
规范 from / to / granularity，限制最大 366 天
  ├─ 会话趋势：按 DAY、WEEK 或 MONTH 查询，再补齐没有数据的时间点
  ├─ 客服排行：按接待会话数取前 10 名
  ├─ 首次响应：计算客服第一条回复与会话开始的平均间隔
  ├─ 时长分布：按固定区间统计并补 0
  ├─ 满意度：评价数、平均分等；无记录时返回空指标对象
  └─ 工单分布：OPEN / IN_PROGRESS / WAITING_USER / RESOLVED 固定顺序补 0
```

“补 0”位于服务层而非前端：SQL 只返回实际存在的分组，`fillTrend`、`fillDurationBuckets` 和 `fillTicketStatuses` 将结果归一为稳定结构，避免图表因某一时段没有数据而缺列或错位。

### 3.12 用户、角色与权限变更

**用户管理的关键约束**

- `UserServiceImpl.create` 检查用户名和可选 ID 唯一性，使用 `PasswordUtil.hash` 保存密码，VIP 等级通过统一函数归一化。
- 禁用用户、管理员重置密码和删除用户后都会调用 `TokenServiceImpl.revokeAllForUser`，使旧登录状态立即失效。
- 默认管理员不能被禁用或删除，也不能移除 `ADMIN` 角色，避免系统失去管理入口。
- `assignRoleToUser` 只允许分配启用角色；关系 Mapper 使用 `INSERT IGNORE`，重复请求不会产生重复关系。

**角色与权限管理的关键约束**

1. 角色编码统一转为大写并检查唯一；权限编码和请求方法由 `RbacServiceSupport` 统一规范化。
2. `ADMIN`、`AGENT`、`USER` 三个基础角色不能删除；被聊天或管理流程使用的基础权限也禁止删除。
3. 禁用的角色不能再分配权限，禁用的权限也不能被分配。
4. 不能移除 `ADMIN` 的用户管理、角色管理和权限管理三项核心权限，防止所有管理员同时失去修复权限配置的能力。
5. 角色—权限和用户—角色关系写入采用幂等插入；删除操作先做基础对象与保护规则检查。

这里的 Controller 权限检查只是入口保护，服务层仍保留不可删除、不可禁用和不可移除等业务约束。因此管理脚本或未来新增入口也必须调用现有服务，不能绕过服务直接操作 Mapper。

### 3.13 管理员创建、删除会话与附件收尾

**`ChatAdministrationService.createSession`**

管理员输入普通用户和客服的登录编号后，服务分别检查账号存在且启用、角色分别包含 `USER` 与 `AGENT`，并确认普通用户没有活动会话。随后复用 `ChatSessionOperations.createSession` 创建会话并通知双方，避免管理员入口复制一套 Redis 分配逻辑。

**`ChatAdministrationService.deleteSession` 与 `ChatSessionDeletionService.deleteSession`**

```text
读取会话
  ├─ 仍为 ACTIVE 且有客服：先复用 endSessionByAgent 完成负载和 Redis 状态结算
  └─ 已结束：直接进入删除服务
        → 预先读取全部附件 storedName
        → 删除关联工单
        → 删除 chat_session，数据库外键级联清理消息、已读、标签、评价和附件记录
        → 事务提交后逐个删除 MinIO 原文件
```

附件对象删除放在 `afterCommit`：如果数据库事务回滚，原文件仍保留；数据库已提交但对象删除失败时只记录包含 `sessionId` 和 `storedName` 的错误日志，供后续清理任务处理。管理员单独删除消息只删除数据库记录，不走普通用户的撤回窗口，也不会伪造撤回事件，因此属于高权限维护操作。

### 3.14 前端实时事件归并与请求防串

`frontend/src/stores/chat.js` 是三个工作台共享的聊天状态中心，但连接、会话动作和客服动作分别拆到 `chat-connection.js`、`chat-session-actions.js`、`chat-agent-actions.js`，主 Store 重点负责把 HTTP 初始数据、STOMP 增量事件和本地乐观状态归并起来。

**`_handleChatEvent` 的处理顺序**

- `CHAT_HISTORY`：先核对 `requestId`，只接收当前历史请求；根据对方已读水位线标记我方历史消息，再与现有消息合并去重。
- 新消息：对别人发来的消息先发送 ACK；当前会话可见时标记已读，否则增加对应会话未读数；最后更新会话列表摘要。
- 排队与分配事件：通过 `_queueLifecycleVersion`、开始/取消状态和请求序号避免“取消后旧请求返回”把用户重新标成排队中。
- 会话创建、恢复、转接和结束：客服刷新工作视图，普通用户刷新会话与排队状态，并只在目标会话已经进入列表后选中它。
- 工单事件：区分表单是否已编辑，避免远端推送覆盖尚未提交的本地内容。

消息发送采用 `clientMsgId` 建立本地乐观消息。服务端返回同一 `clientMsgId` 时，用真实 `messageId` 和状态替换临时消息；超时或 STOMP 错误则标记失败，用户重试仍沿用后端幂等边界。会话列表、历史、工单和转接日志各自维护请求序号，晚返回的旧请求不会覆盖当前选中会话的数据。

### 3.15 离线消息重放与客户端 ACK

这里的“离线消息”更准确地说是“接收方还没有确认的消息”。`ChatOfflineMessageService.cacheForReceiver` 把完整消息 JSON 追加到 `offline:msg:{receiverId}`，并设置按天计算的过期时间。列表不会为了控长度直接截断，因为消息落库前后都可能依赖它重投。

**`pullOfflineMessages` 的处理方式**

1. 先查 `user:ws:{userId}`。用户当前没有 WebSocket 会话时直接返回，不做无意义推送。
2. 读取接收者自己的待确认列表，逐条反序列化并推送。推送成功也暂不删除，必须等客户端 ACK。
3. 某条 JSON 已损坏时，将这条脏数据从列表移走。它继续留在队列里只会导致每次重放都失败。
4. 普通推送异常时保留原记录，留给下一次拉取。单条失败不会拦住后面的消息。
5. 遍历完成后发送 `OFFLINE_MESSAGES_REPLAYED`，前端据此刷新会话视图。

**`handleAck` 为什么不能按 messageId 直接删除**

服务先在当前接收者的离线列表中查找这条消息。找不到就拒绝确认，避免用户拿着别人的 messageId 删除对方消息。匹配后才从列表删除 JSON，并在 `msg:ack:{messageId}` Set 中加入接收者 ID。重复 ACK 命中 Set 后直接返回。

代码还兼容早期 Hash 格式的 ACK Key。发现旧类型时会先核对其中的 `receiverId`，再迁成 Set，防止升级后直接触发 Redis `WRONGTYPE`。

### 3.16 客服上线、会话恢复与空闲容量补位

`ChatAgentService.agentOnline` 会先清掉重连宽限期，再调用 `ChatAgentSessionRecoveryService.restoreActiveSessions` 找回这个客服仍在处理的会话，最后按查询结果重建 `agent:load`。如果只把客服加入在线集合，已有会话数就会丢失，后续分配可能超过坐席容量。

恢复时优先读取 `agent:{agentId}:sessions`。服务把会话 ID 分批交给 MySQL 查询，只保留“仍属于该客服且状态为 ACTIVE”的记录，并顺手从 Redis 移除失效 ID。索引为空或查不到有效会话时，才按客服 ID 和活动状态查询 MySQL。最后把有效会话写回索引，并按创建时间排序返回。

上线通知完成后，`fillAvailableCapacity` 会按 `AGENT_MAX_CONCURRENCY` 计算剩余席位，多次调用 `dequeueAndReassign` 从队列补人，直到坐席已满或队列为空。这样一名客服重新上线后，不需要等待下一次全局调度才开始接待。

VIP 技能以 `chat_agent_skill` 为数据库事实。启用或停用技能后，事务提交回调才重建 Redis 的 `agent:skill:vip`；数据库失败时缓存不会提前变化。管理员按登录编号操作时，服务仍会检查账号存在、启用并具有 `AGENT` 角色。

### 3.17 三类会话状态对账

`ChatSessionReconciliationService` 处理分配、活动会话和结束结算三个阶段留下的半完成状态。

| 对账函数 | 要解决的问题 | 判断依据 |
| --- | --- | --- |
| `reconcilePendingAssignments` | Redis 已预留客服，但数据库会话可能没有创建完成 | 60 秒前的 `assignment:pending`、预留客服和 MySQL 活动会话 |
| `reconcileActiveSessionState` | MySQL 有活动会话，但 Redis 索引缺失、指向旧客服或负载不准 | 分页扫描 MySQL 中的 ACTIVE 会话 |
| `reconcilePendingSessionFinalizations` | 会话结束过程中数据库或 Redis 只完成了一边 | 10 秒前的 `session:finalize:pending` 及其 payload |

待分配对账会遇到三种结果。MySQL 没有活动会话时，释放之前占用的客服容量并让用户重新排队；会话客服与预留客服一致时，补齐 Redis 会话状态和客服负载；两者不一致时，只回滚旧预留，不能破坏已经成立的新会话。

活动会话对账使用游标和批次大小扫描，避免一次读完全部会话。发现 Redis 仍把会话挂在旧客服名下时，先从旧客服集合移除，再调用 `cacheActiveSessionState` 重建完整索引。一个扫描周期走到末尾后删除游标，下一轮从头开始。

结束状态对账会解析待结束 payload 中的请求时间。数据库仍未关闭时先补做 `endSession`，确认状态已经变成 `CLOSED` 后，再执行 Redis 结算。单个会话出错只记录日志，后面的会话继续处理，失败项也会留给下轮重试。

### 3.18 注册、恢复码与密码重置

`UserAccountServiceImpl.register` 在同一事务中完成用户写入、默认 `USER` 角色分配和恢复码生成。创建前会确认默认角色存在且启用；数据库唯一键仍是最后一道并发保护，重复用户名最终转换为业务冲突。

恢复码由 8 个随机字节生成，显示为分段十六进制字符串。数据库只保存 `PasswordUtil.hash` 后的值和过期时间，原文只在生成时返回给用户。

**`resetPassword` 的具体思路**

1. 用户名不存在、恢复记录不存在、已经过期或散列不匹配时统一返回“用户名或恢复码错误”，不向外透露是哪一项不对。
2. 账号必须处于启用状态，新密码不能与旧密码相同。
3. `consumeRecoveryCode` 同时匹配用户 ID、旧散列和有效期并执行条件删除。恢复码在这里完成单次消费，两个并发重置请求最多只有一个能删除成功。
4. 更新密码后马上生成下一枚恢复码，并撤销该用户的全部 Token。旧密码、旧恢复码和其他设备的登录状态都会失效。

用户在已登录状态下修改密码也会撤销全部 Token。重新生成恢复码则只替换恢复记录，不会改密码。

### 3.19 历史附件迁移与孤儿对象清理

`ChatAttachmentMigrationService.migrate` 先把配置中的旧存储目录转成绝对规范路径，再遍历数据库中的附件记录。每条记录都要检查 `storedName`：不能为空、不能包含 `..`，也不能是绝对路径。解析后的源文件还必须位于旧目录之下。

本地文件存在时，迁移会先比较数据库记录的文件大小，再计算 SHA-256、上传 MinIO，然后从对象存储重新读取，复核大小和摘要。本地文件已经不存在时，服务不会直接当成迁移成功，而是检查 MinIO 中是否已有同名且大小一致的对象。

全部记录处理后，服务还会扫描旧目录。如果里面有数据库未登记的普通文件，就停止删除。确认没有遗漏后，旧目录先原子改名为 `.pending-delete`，再从子项到父目录逐层删除。改名把“仍在使用的目录”和“已经确认待删的目录”分开，即使清理中断，也不会让下一次启动误以为迁移尚未开始。

日常孤儿清理由 `ChatAttachmentCleanupScheduler` 负责。它使用分布式调度锁，默认首次等待 5 分钟，之后每天执行一次。这个任务清理对象存储中的无引用文件，不替代上述一次性迁移校验。

### 3.20 HTTP 与 STOMP 异常如何到达前端

HTTP 和 STOMP 使用两套异常出口，因为它们的返回通道不同。

`WebExceptionAdvice` 把 Bean Validation、JSON 解析失败、资源不存在、未登录、无权限和业务状态冲突转换为 `Result<Void>`。大多数 `IllegalArgumentException` 只对客户端返回“请求参数不正确”，详细原因写入服务端日志；`BusinessStateException` 返回 409，并保留可以指导用户刷新或重试的业务提示。未捕获异常统一返回 500，不把堆栈或内部类名放进响应。

`StompExceptionHandler` 把异常发到当前连接自己的 `/user/queue/errors`，并设置 `broadcast=false`，同一账号的其他 WebSocket 会话不会收到这次错误。业务冲突使用 `CONFLICT`，权限不足使用 `FORBIDDEN`，参数和系统错误使用 `ERROR`。前端收到错误事件后，需要同时结束对应的加载或乐观状态，不能只弹一条提示。

### 3.21 STOMP 应用服务的二次校验

`ChatStompController` 很薄，真正的入口校验在 `ChatStompApplicationService`。每个方法先从 `Principal` 取当前用户，客户端请求中的发送者 ID 不参与身份判断。结束和转接会话还会重新查询角色与权限，因为 STOMP 消息不会经过 Shiro 的 HTTP 过滤器。

`requireValidStompPayload` 会主动调用 Jakarta Validator。代码没有完全依赖方法参数上的 `@Valid`，原因是 STOMP 在不同消息转换路径下不一定自动触发 Bean Validation。`handleSend` 在此基础上又对白名单字段做一次检查：会话 ID 和 `clientMsgId` 最多 64 个字符，类型只能是 `TEXT`、`IMAGE` 或 `FILE`，正文不能为空且最多 4000 个字符。

历史消息返回时，应用服务不只放入消息列表。响应还带原请求的 `requestId`、下一页游标、是否还有更多、未读数和对方已读水位线。前端用 `requestId` 丢弃已经过时的响应，用水位线恢复刷新前的已读显示。

### 3.22 在线状态写入和旧连接清理

`ChatPresenceStateStore.refreshOnlineState` 同时维护五类数据：用户在线 Hash、用户到 WebSocket 的正向映射、WebSocket 到用户的反向映射、在线用户 Set 和心跳超时 ZSET。ZSET 的 score 保存的是“超时截止时间”，不是最近一次心跳时间，调度器因此可以直接查询 `score <= 当前时间` 的用户。

同一用户建立新连接时，方法会先删除旧 WebSocket 的反向映射。旧浏览器稍后触发断开事件时，就无法再通过旧会话 ID 找到用户，也不会误删新连接状态。

**`cleanupOnlineState` 的原子判断**

清理脚本先比较 `user:ws:{userId}` 中记录的会话 ID 和本次要清理的会话 ID。两者不同说明用户已经重连，脚本立即返回，不碰任何在线数据。只有匹配时才删除在线 Hash、正向映射、正确的反向映射，并从在线 Set 和心跳 ZSET 移除用户。这个判断必须和删除写在同一段 Lua 中，Java 先读后删会留下重连竞态。

### 3.23 无活动会话如何结束并重新分配

`ChatSessionInactivityService.handleSessionInactivityTimeout` 收到的是候选会话和本轮截止时间。它会重新读 MySQL；会话已不存在或不再是 ACTIVE 时，只清理 `session:last-activity` 中的旧索引。

活动会话要先取得用户级分配锁。用户仍在线时，系统尝试预留另一名客服，并排除当前客服；没有可用客服时，本轮暂不结束会话。用户已经离线则不需要新客服，可以直接进入结束流程。

`finalizeSession` 会再次检查最后活动时间。如果用户在扫描后刚发来消息，Redis 中的时间会晚于本轮 cutoff，结束操作随即取消。会话确实超时后，系统关闭旧会话并通知双方。此前已预留新客服的，会创建一条新会话；创建失败则释放预留、把用户放回队列并推送当前位置。最后，旧客服释放出的席位继续接待队列用户。

活动时间、分配锁、客服预留和新旧两条会话记录共同决定这次超时处理的结果。`cutoff` 用于阻止扫描后的新消息被误判为超时；目标客服的预留记录与新会话创建结果决定是否完成重新分配。

### 3.24 `finalizeSession` 的事务与补偿顺序

`ChatRoutingSessionSupport.finalizeSession` 被主动结束、断线处理和无活动超时共同复用，执行顺序不能随意调整。

```text
取得 session:operation:lock 并启动续租
  → 重新读取会话，确认仍为 ACTIVE、客服未变化
  → 如果是超时关闭，再核对 lastActivity <= cutoff
  → 先登记 session:finalize:pending
  → 条件更新 MySQL 为 CLOSED
  → 记录 VIP 解决时长
  → 注册 afterCommit，事务提交后执行 Redis 结算脚本
  → 停止续租并按 Token 释放会话锁
```

先写 pending 是为了覆盖“MySQL 已关、Redis 未清”的时间窗。Redis 结算脚本会删除用户活动会话、会话双方映射、客服会话集合和最后活动索引，同时减少客服负载并清掉 pending。若提交后的脚本失败，对账任务仍能根据 payload 补做结算。

`chatSessionMapper.endSession` 影响 0 行时，函数不会马上当成失败。它重新读取会话：如果别的线程已经把会话正常关闭，就沿用数据库中的结束时间继续收尾；如果状态仍未关闭，pending 留给后续对账。

### 3.25 附件内容识别和压缩包检查

扩展名白名单只能限制文件名，`AttachmentContentValidator.validate` 还会检查文件内容。JPEG、PNG、GIF、WebP、PDF 和旧版 Office 文件按文件头识别；txt 会拒绝 NUL 和不允许的控制字符；zip、docx、xlsx、pptx 都必须以 ZIP 文件头开始。

ZIP 类文件会继续解包检查。最多接受 1000 个条目，累计解压内容不能超过 50 MB，压缩比不能超过 100。条目名包含绝对路径、`..` 或反斜杠时直接拒绝，避免路径穿越。对于 OOXML 文件，还必须同时找到 `[Content_Types].xml` 和对应的 `word/`、`xl/` 或 `ppt/` 目录。把普通 zip 改名成 docx 过不了这一层。

这些检查针对当前聊天附件范围，并不是通用杀毒功能。新增文件类型时，需要同时修改扩展名白名单、文件头判断、消息类型校验和前端预览分支，不能只改上传接口允许的后缀。

### 3.26 LibreOffice 预览子进程

`LibreOfficePreviewConverter.convertToPdf` 为每次转换创建独立临时目录，并把 LibreOffice 的用户配置目录也放进去。这样并发转换不会争用同一个 profile。源文件固定写成 `source.<扩展名>`，命令使用 headless 模式把结果输出到同一目录。

进程在配置的超时时间内没有退出时，代码会强制结束它并返回预览超时。正常退出也不代表转换成功，服务还会检查 `source.pdf` 是否存在、大小是否超过上限，并核对开头是否为 `%PDF-`。线程被中断时会恢复中断标记，再抛出业务异常。

finally 会从文件到目录逆序清理整个工作区。临时目录清理异常只记录警告，已生成的预览结果照常返回。

### 4.1 主要 HTTP 接口分组

| 路径前缀 | Controller | 用途 |

## 5. 数据模型与 Redis 状态

### 5.1 MySQL 表分组

SQL 脚本位于 `sql/`，Compose 在**全新 MySQL volume**的第一次启动时依次执行 `user_ddl.sql`、`rbac_ddl.sql`、`chat_ddl.sql`。

| 分组 | 表 | 主要用途 |
| --- | --- | --- |
| 账号 | `sys_user`、`sys_password_recovery` | 用户资料、账号状态、VIP 等级、密码恢复码 |
| 权限 | `sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission` | RBAC 角色和权限关系 |
| 会话 | `chat_session`、`chat_session_tag`、`chat_session_transfer_log`、`chat_session_rating` | 会话主体、标签、转接审计和评价 |
| 消息 | `chat_message`、`chat_message_read` | 消息正文、客户端幂等标识和已读状态 |
| 工单 | `support_ticket`、`support_ticket_status_history` | 会话关联工单及状态变更历史 |
| 客服效率 | `chat_agent_skill`、`chat_quick_reply` | VIP 接待技能和客服个人快捷回复 |
| 附件 | `chat_attachment` | 对象名、原始文件信息、会话及上传者归属 |

**重要约束**

- `chat_session` 是会话最终状态的持久化事实来源；Redis 只保存活动索引和实时辅助状态。
- `chat_message` 的客户端幂等信息由 `sessionId`、`senderId` 与 `clientMsgId` 共同确定。
- 管理员删除会话或消息会影响历史数据，相关记录需区分正常业务删除与演示环境重置。

### 5.2 Redis Key 分组

| 分组 | Key/模式 | 类型与说明 |
| --- | --- | --- |
| 在线 | `user:online:{userId}`、`user:ws:{userId}`、`ws:session:{wsId}`、`online:heartbeat` | Hash/String/ZSET，记录连接、最后心跳和超时扫描索引 |
| 分配 | `agent:load`、`agent:last-assigned`、`agent:{agentId}:sessions` | ZSET/ZSET/Set，记录客服负载、公平性顺序和客服持有会话 |
| 排队 | `queue:pending`、`queue:enqueued-at`、`queue:normal-due`、`queue:vip-level` | ZSET/Hash 等，维护顺序、真实入队时间、反饥饿和 VIP 信息 |
| 会话 | `user:active:session:{userId}`、`session:user:{id}`、`session:agent:{id}`、`session:meta:{id}`、`session:last-activity` | 活动会话互查、元数据和无活动超时索引 |
| 消息 | `session:msg:{sessionId}`、`offline:msg:{userId}`、`msg:ack:{messageId}`、`client:msg:dedup:*` | 热消息、离线消息、接收确认和发送幂等 |
| 落库可靠性 | `persist:pending`、`persist:pending:payload:{id}`、`persist:retry:lease:{id}`、`persist:deadletter` | 待落库、完整 payload、互斥 lease、失败死信 |
| 并发控制 | `chat:assign:lock:*`、`session:operation:lock:*`、`presence:operation:lock:*`、`scheduler:lock:*` | 分配、会话操作、在线状态和调度器锁 |
| VIP 统计 | `agent:skill:vip`、`stats:vip:wait`、`stats:vip:resolve`、`vip:callback:pending` | VIP 技能、等待/解决时长及全员离线时的回呼待办 |

会话、排队和待落库状态包含多组关联索引。状态修复可通过现有对账任务完成；人工删除 Key 前需要备份并明确影响范围。

## 6. 容器化部署与运行维护

### 6.1 一键启动结构

`docker compose up -d --build` 会启动以下四个服务：

| 服务 | 镜像/构建方式 | 作用 | 健康检查 |
| --- | --- | --- | --- |
| `mysql` | `mysql:8.4` | 业务持久化；首次启动执行 SQL 建表脚本 | `mysqladmin ping` |
| `redis` | `redis:8-alpine` | 实时状态、队列、缓存与锁；开启 AOF | `redis-cli ping` |
| `minio` | 固定版本 MinIO | 附件对象存储和预览文件 | `mc ready local` |
| `app` | 根目录 `Dockerfile` 构建 | Vue 静态资源 + Spring Boot 应用 + LibreOffice | `/actuator/health` |

### 6.2 首次部署步骤

```powershell
Copy-Item .env.example .env
# 编辑 .env，把所有 change-this- 开头的密码替换为安全值
docker compose up -d --build
docker compose ps
```

当 `app`、`mysql`、`redis`、`minio` 全部显示运行或健康后，访问 `http://localhost:8080/frontend/`。若修改 `APP_PORT`，替换地址中的端口号。

`.env` 包含 MySQL、Redis、MinIO 和首次管理员密码，属于部署机密，并由 Git 忽略。首次管理员密码在管理员账号不存在时生效；后续修改 `.env` 保留既有管理员密码。

### 6.3 数据与故障处理

- MySQL、Redis、MinIO 分别使用命名 volume 保存数据；`docker compose down` 保留数据，`docker compose down --volumes` 会删除全部数据卷。
- `docker compose ps` 用于确认服务健康，`docker compose logs --tail 200 app` 用于查看应用启动、数据库连接和配置错误。
- 附件异常主要查看 `minio` 与 `app` 日志；实时聊天异常涉及浏览器 WebSocket、登录 Token、Redis 和 STOMP/心跳日志。

| 修改消息发送或撤回 | 幂等键、限流、附件引用校验、pending payload、异步落库、死信、发送者 ACK 与热缓存同步 |

| 删除会话或用户 | 活动会话先结算、数据库外键影响、事务提交后对象清理和旧 Token 注销 |
