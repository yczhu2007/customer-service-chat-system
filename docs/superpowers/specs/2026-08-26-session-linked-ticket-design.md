# 会话关联轻量工单设计

## 1. 背景与目标

当前系统已经具备实时会话、客服分配、消息与附件、会话标题、优先级、分类、标签、归档和审计能力。下一阶段在此基础上增加轻量工单，使问题在实时聊天结束后仍可持续跟踪。

本阶段的目标是：

- 客服可以从自己负责的会话创建一张工单。
- 用户和负责客服可以在该会话中查看工单详情。
- 客服可以更新工单状态、问题描述和处理结果。
- 工单更新通过现有 STOMP 通道实时同步给会话双方。
- 会话生命周期与工单处理生命周期相互独立。

## 2. 范围边界

本阶段采用“一次会话最多关联一张工单”的轻量模型。

包含：

- 工单创建、查询和更新。
- 工单编号、状态、问题描述、处理结果和时间信息。
- 用户只读视图和客服编辑视图。
- 基于会话参与关系的访问控制。
- 工单创建与更新事件的实时通知。
- 并发创建和并发更新保护。

不包含：

- SLA、超时升级和自动化规则。
- 邮件、电话等外部渠道自动建单。
- 自动分派、工单合并、子工单和多会话关联。
- 知识库、内部评论和单独的工单附件。
- 独立的管理员工单管理中心。
- 工单物理删除。

## 3. 领域边界

### 3.1 会话职责

`ChatSession` 继续负责：

- 实时聊天状态 `ACTIVE / CLOSED`。
- 用户和负责客服。
- 标题、优先级、分类和标签。
- 消息、附件、转接、归档和评价。

### 3.2 工单职责

`SupportTicket` 负责：

- 稳定、可展示的工单编号。
- 独立的问题处理状态。
- 问题描述和处理结果。
- 创建、更新和解决时间。
- 并发更新版本。

工单标题、优先级、分类、标签、用户和客服从关联会话读取，不在工单表中重复保存。

### 3.3 生命周期

工单状态限定为：

- `OPEN`：待处理。
- `IN_PROGRESS`：处理中。
- `WAITING_USER`：等待用户。
- `RESOLVED`：已解决。

允许的状态变化：

- `OPEN` 可以变为 `IN_PROGRESS`、`WAITING_USER` 或 `RESOLVED`。
- `IN_PROGRESS` 可以变为 `WAITING_USER` 或 `RESOLVED`。
- `WAITING_USER` 可以变为 `IN_PROGRESS` 或 `RESOLVED`。
- `RESOLVED` 可以重新变为 `IN_PROGRESS`。

工单不设置 `CLOSED`，避免与会话关闭状态重复。工单处于 `RESOLVED` 时记录 `resolved_at`；重新进入处理中时清空该时间。

## 4. 数据设计

新增 `support_ticket` 表：

| 字段 | 类型建议 | 约束与含义 |
| --- | --- | --- |
| `id` | `BIGINT` | 自增主键 |
| `session_id` | `VARCHAR(64)` | 非空、唯一、外键关联 `chat_session.id` |
| `status` | `VARCHAR(20)` | 非空，默认 `OPEN` |
| `description` | `VARCHAR(1000)` | 非空，问题描述 |
| `resolution` | `VARCHAR(1000)` | 可空，处理结果 |
| `version` | `INT` | 非空，默认 `0`，用于乐观并发控制 |
| `created_at` | `DATETIME(6)` | 非空 |
| `updated_at` | `DATETIME(6)` | 非空 |
| `resolved_at` | `DATETIME(6)` | 可空 |

对外工单编号由主键稳定格式化为 `TK-` 加八位数字，例如 `TK-00000125`。数据库和服务内部仍使用主键，不增加每日序列表或额外编号生成器。

`session_id` 唯一约束是重复建单的最终保护。删除会话时不级联删除工单；已有工单的会话不允许物理删除，以保留处理记录。

## 5. 后端设计

### 5.1 分层

- `commonModel`：`SupportTicket`、Mapper、请求 DTO 和返回 VO。
- `businessModel`：工单查询、创建、状态转换、权限和并发控制。
- `application`：HTTP Controller、异常映射和 STOMP 通知入口。

沿用 MyBatis-Plus、现有 `Result` 返回结构和认证/RBAC机制，不新增依赖。

### 5.2 接口

#### 查询会话工单

```http
GET /chat/sessions/{sessionId}/ticket
```

- 会话用户、负责客服和管理员可调用。
- 没有关联工单时返回成功且 `data` 为 `null`，前端显示未创建状态。

#### 创建工单

```http
POST /chat/sessions/{sessionId}/ticket
```

请求体：

```json
{
  "description": "用户无法完成订单支付"
}
```

- 仅当前负责客服可以创建。
- ACTIVE 和 CLOSED 会话均允许创建。
- 同一会话重复创建返回业务冲突，不生成第二张工单。

#### 更新工单

```http
PATCH /chat/tickets/{ticketNo}
```

请求体：

```json
{
  "status": "IN_PROGRESS",
  "description": "用户无法完成订单支付",
  "resolution": null,
  "version": 0
}
```

- 仅当前负责客服可以更新。
- 必须满足状态转换规则。
- `version` 不一致时拒绝覆盖并提示刷新。
- 设置为 `RESOLVED` 时处理结果必须非空。

### 5.3 权限规则

- 用户只能读取 `session.user_id` 等于当前用户的工单。
- 客服只能创建和更新 `session.agent_id` 等于当前客服的工单。
- 管理员本阶段仅允许读取，不提供管理入口。
- 所有权限判断使用认证后的内部用户 ID，不接受客户端传入用户或客服 ID。

### 5.4 一致性与事务

- MySQL 是工单唯一事实来源，工单不写入 Redis 缓存。
- 创建工单使用数据库唯一约束处理并发重复请求。
- 更新使用 `WHERE id = ? AND version = ?`，成功后版本加一。
- 数据库事务提交后再发送 STOMP 通知，通知失败不回滚已提交的工单。
- 通知失败记录脱敏日志；前端下次打开会话时仍可通过 HTTP 取得最新数据。

## 6. 实时事件设计

复用现有用户队列和客服队列，新增事件类型：

- `TICKET_CREATED`
- `TICKET_UPDATED`

事件只携带：

```json
{
  "type": "TICKET_UPDATED",
  "sessionId": "会话ID",
  "ticketNo": "TK-00000125",
  "version": 1
}
```

前端仅在事件的 `sessionId` 等于当前会话时重新请求工单详情。通知不携带完整问题描述和处理结果，减少旧数据覆盖与越权泄露风险。

## 7. 前端设计

### 7.1 状态管理

聊天 Store 增加当前工单、加载状态、错误状态和请求序号。切换会话时取消旧请求的展示资格，避免旧会话响应覆盖当前工单。

### 7.2 客服端

在现有会话元数据区域下方增加“关联工单”面板：

- 未创建时显示说明和“创建工单”按钮。
- 已创建时显示工单编号、状态、问题描述、处理结果、创建时间和更新时间。
- 客服可以编辑状态、描述和处理结果并保存。
- 工单编号只读，不展示内部主键或会话 UUID。

### 7.3 用户端

在当前会话详情中增加只读工单卡片，显示：

- 工单编号。
- 会话标题。
- 工单状态。
- 会话优先级和分类。
- 负责客服昵称。
- 问题描述、处理结果和更新时间。

没有工单时不显示空表单，只显示“该会话暂未创建工单”。

### 7.4 显示规则

- 前端状态使用中文，后端枚举保持英文。
- 继续复用现有优先级、分类和标签中文映射及颜色。
- 使用现有 Element Plus 组件和项目样式，不引入新的 UI 库。

## 8. 错误处理

- 会话不存在：返回统一的资源不存在提示。
- 非会话参与者查询：返回 403。
- 非负责客服创建或修改：返回 403。
- 重复创建：返回 409，前端重新加载已有工单。
- 非法状态或状态转换：返回 400 和明确中文提示。
- 并发版本冲突：返回 409，提示“工单已被其他操作修改，请刷新后重试”。
- STOMP 通知失败：不回滚数据库事务，由日志和后续 HTTP 查询恢复界面。

异常响应不包含 SQL、内部类名、堆栈或内部用户 ID。

## 9. 测试与验收

### 9.1 后端测试

- 负责客服可以为 ACTIVE 和 CLOSED 会话创建工单。
- 普通用户、其他客服不能创建或更新。
- 会话用户、负责客服和管理员可以查询；无关用户不能查询。
- 同一会话并发创建只能成功一次。
- 合法状态转换成功，非法转换失败。
- 解决工单必须填写处理结果。
- 版本冲突不会覆盖较新的数据。
- 事务提交后才发送实时事件。

### 9.2 前端测试

- 客服端无工单时显示创建入口，有工单时显示编辑表单。
- 用户端只显示只读信息，不出现编辑按钮。
- 切换会话时不会显示上一个会话的工单。
- 收到当前会话工单事件后重新加载。
- 收到其他会话工单事件时不打断当前输入。
- 并发冲突和权限错误显示明确提示。

### 9.3 演示验收

1. 用户发起咨询，客服接入。
2. 客服从当前会话创建工单，双方看到相同工单编号。
3. 客服将状态改为处理中，用户界面实时更新。
4. 客服填写处理结果并设为已解决。
5. 聊天关闭后，用户重新打开历史会话仍能查看工单。
6. 另一个用户不能读取该工单。
7. 重复创建和并发覆盖被系统阻止。
